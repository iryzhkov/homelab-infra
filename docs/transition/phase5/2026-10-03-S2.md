All six: `replicas: 1`, constraint `node.labels.gpu == intel`, `restart_policy: any`, stop-first.
No snapshot: nothing here is state worth one (gatus-public history and the Piper cache are
disposable, by the plan).

Per stack, the reasoning:

- adguard. The credentials leave the world-readable Compose copy (`~/app/adguard/adguardhome-sync.yaml`,
  root 0644): the preparation renders the same template
  (`stacks/adguard/templates/adguardhome-sync.yaml.j2`, secrets from
  `secrets/homelab-adguard-sync.sops.yaml`) owned by the container's uid 1001 (`docker inspect`
  `Config.User` = `1001`) with mode 0400. A bind file rather than a Swarm config or secret:
  `roles/swarm/tasks/stack.yml` renders the stack before it runs `prepare_tasks`, so a file the
  preparation writes cannot take part in the render or in a hash-named config; a bind plus a
  forced update gives the same restart-on-change. Any change phase 4 makes to
  `adguard_instances` reaches it through the shared template. The old 0644 copy stays on
  homelab until cleanup and should be deleted then.
- gatus-public. Loses the address bind (Swarm publishes on every interface; the ingress filter
  keeps 3001 off VLAN 60 and the mesh). The Swarm volume is named `gatus-public_gatus-data`,
  the Compose volume's name, so on homelab history continues; on normandy it starts empty.
- voice. The Caddyfile and `site/index.html` are not in this repository; the preparation
  mirrors them from `~/app/voice` on homelab (the source stays there) to both workers. A
  Caddyfile change forces an update; a site change is served live. Bringing both files into
  `stacks/voice/` would remove the dependence on homelab's directory; later item.
- wyoming-openai. Environment only. Loses the address bind like gatus-public. Home Assistant
  keeps working through the mesh while homelab is up.
- wyoming-piper. The preparation seeds `/srv/swarm/wyoming-piper/data` on homelab once from the
  Compose volume (`rsync --ignore-existing`, handed to uid 1000), then copies it to normandy
  without `--delete` (either copy may gain voices). 671 MB, eight voices (16 files: each `.onnx` with its `.json`).
- whisper. The model is mirrored from `~/app/whisper/models` on homelab. `cpus: "3"`, not the
  plan's 4: both workers have four vCPUs (`nproc` 4 on each), so a limit of 4 is no limit,
  and on normandy whisper would compete with Frigate and Immich; `--threads 4` is kept.
  normandy's CPU (`i5-9500`, `avx2`) runs the dispatch build per the Compose file's notes.

## Activation and cutover plan (stage 2)

As in S1: move one entry from `pending_swarm_stacks_s2` to `swarm_stacks_s2`, run `swarm.yml
--tags stacks -e only=<name> -e swarm_cutover=<name>`, then `traefik.yml` and `site.yml -l
homelab,normandy -e only=gatus`. The preparation runs inside the cutover run, before the
Compose project is removed, so the files are in place when the service starts.

Order: adguard, gatus-public, voice, whisper, wyoming-openai, wyoming-piper (whisper before
wyoming-openai, so a failed whisper rollback does not leave Home Assistant on a moved proxy).

## Open questions for the lead

- The common rules say not to touch AdGuard. adguardhome-sync is the sync container on
  homelab, not the AdGuard LXCs, and the migration plan assigns it to S2; this batch only
  moves the container. If phase 4 is still changing the AdGuard instances at cutover time,
  the lead may want adguard last.
- `roles/swarm/tasks/stack.yml` renders the stack before `prepare_tasks`, so the plan's
  convention "env_file: ./secrets.env written by swarm-prepare.yml" cannot work on a first
  deploy (the render does not find the file) and lags one run behind afterwards. This batch
  avoids it (bind files plus forced updates). F and P batches that rely on it need the order
  changed in the role.
