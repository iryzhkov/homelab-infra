All 18 F1 to F5 `swarm-prepare.yml` files share one body (only the list of copies and, for navidrome and F2, a NAS check differ). What it does: in the cutover run only (`swarm_cutover == <name>`) and only while `/srv/swarm/<name>/.swarm-owner` is absent on the pinned node, it (1) copies the Compose state into `/srv/swarm/<name>/...` with `rsync -a --numeric-ids --delete` while Compose still runs, (2) `docker stop`s the Compose project's containers (by the `com.docker.compose.project` label), (3) copies again from quiescent files, (4) writes `.swarm-owner` naming the node. Outside the cutover it only reads (`docker node ls`, `stat`). A re-run after a failed deploy finds `.swarm-owner` and copies nothing, so it cannot overwrite what the Swarm service wrote. The Compose directory is left untouched as the rollback copy. This matches the order and contract in the current `roles/swarm/tasks/stack.yml` (prepare before render; cutover-only actions gated).

## How the entries are kept inactive, and how to activate one

Every reader of Swarm stacks (playbooks/swarm.yml, site.yml's skip list, the Traefik generator, Gatus, the backup role, swarm-move.yml, `filter_plugins/stacks.py`) reads only variables named `swarm_stacks_*`. The F entries are in `pending_swarm_stacks_f<N>`. To activate one stack, in the same change as its cutover: move its entry unchanged into a list `swarm_stacks_f<N>` in the same file (create the list with the first entry), then run in order:

1. `ansible-playbook playbooks/swarm.yml --tags stacks -e only=<name> -e swarm_cutover=<name>`
2. `ansible-playbook playbooks/traefik.yml`
3. `ansible-playbook playbooks/site.yml -l homelab,normandy -e only=gatus`
4. `ansible-playbook playbooks/backup.yml -l homelab,normandy` (puts the stack into `/etc/swarm-sync/config.json`; without it the hourly job does not know the stack)
