## 1. UniFi: one address group as the source of the eight edge policies

### Before

Command: `GET /proxy/network/v2/api/site/default/firewall-policies` (256 policies) and
`GET /proxy/network/api/s/default/rest/firewallgroup` (four port groups, no address group).
The eight user policies named in `proposals/unifi-edge.md` each had
`source: {matching_target: IP, matching_target_type: SPECIFIC, ips: ["192.168.20.33"]}`.

Baseline through public-api, from the laptop with
`curl -sk -o /dev/null -w '%{http_code}' --resolve <name>:443:192.168.20.33 https://<name>/`:
`vault` 200, `home` 200, `photos` 200, `git` 200, `auth` 302.

Baseline from public-api-b (`curl -s -m 5` to each backend address and port): all eight
targets in section 4 returned `000` (timeout), as expected while only .33 was allowed.

### Calls

1. Create the group:

   ```
   POST /proxy/network/api/s/default/rest/firewallgroup
   {"name":"edge-proxies","group_type":"address-group","group_members":["192.168.20.33","192.168.20.4"]}
   -> rc ok, _id 6ac0765c1825b50cb14c41c0
   ```

2. For each policy, the object as read, with `hits` and `last_hit` removed and the source
   rewritten by
   `.source |= (del(.ips) | .matching_target="IP" | .matching_target_type="OBJECT" | .ip_group_id="6ac0765c1825b50cb14c41c0")`,
   sent as `PUT /proxy/network/v2/api/site/default/firewall-policies/<_id>`. Zigbee2MQTT
   (`6a966d165afbaf142ea88ae6`) went first and was verified on its own (below) before the
   other seven: `6a966cc65afbaf142ea8887a` homelab, `6a966d165afbaf142ea88add` normandy,
   `6a966d165afbaf142ea88ae0` Home Assistant, `6a966d165afbaf142ea88ae3` Proxmox web UI,
   `6a966d175afbaf142ea88ae9` gaming-pc, `6a9cedf55afbaf142ed0f1ce` laptop,
   `6a966d175afbaf142ea88aec` Black Pearl. Each answered with
   `ip_group_id: 6ac0765c1825b50cb14c41c0, ips: []` and no error.

The API accepted the group as a source, so the per-address fallback was not needed. Nothing
was deleted.

### After

On the UDM after the first PUT, `iptables-save` showed the new set in both directions:

```
-A UBIOS_CUSTOM3_LAN_USER -p tcp -m set --match-set UBIOS_6ac0765c1825b50cb14c41c0 src -m set --match-set UBIOS_policy_dst_ip_23 dst ... -j ACCEPT
-A UBIOS_LAN_CUSTOM3_USER ... -m set --match-set UBIOS_6ac0765c1825b50cb14c41c0 dst -m conntrack --ctstate RELATED,ESTABLISHED ... -j ACCEPT
```

Re-read of all policies and diff against the before state (both normalised by `_id`, with
`hits` and `last_hit` removed): 256 policies before and after, none added, none removed,
16 changed, and in every one of the 16 only `source` or `destination` differs:

- the eight user policies: source `ips ["192.168.20.33"]`, `SPECIFIC` became
  `ip_group_id 6ac0765c1825b50cb14c41c0`, `OBJECT`; destination unchanged;
- their eight system `(Return)` policies, regenerated by the UDM: destination
  `ips ["192.168.20.33"]` became `["192.168.20.33", "192.168.20.4"]`; source unchanged.

.3 was not added anywhere.

Through public-api after the change: `vault` 200, `home` 200, `photos` 200, `git` 200,
`auth` 302, `zigbee` 200. Same as before.

Recorded answer: both edge VMs now share one source group; public-api's access is unchanged.

### Rollback

For each of the eight `_id`s, read the policy, then
`PUT .../firewall-policies/<_id>` with
`.source |= (del(.ip_group_id) | .matching_target_type="SPECIFIC" | .ips=["192.168.20.33"])`
(and `hits`, `last_hit` removed). Only when no policy references it any more:
`DELETE /proxy/network/api/s/default/rest/firewallgroup/6ac0765c1825b50cb14c41c0`. Never
delete a policy: removing the last policy of a zone pair also removes its return rule.

## 2. Home Assistant `trusted_proxies`

### Mismatch found first

The brief says to edit `trusted_proxies` in `configuration.yaml`. On the host it is not there:

```
$ grep -rn "trusted_proxies\|^http:\|use_x_forwarded_for\|192.168.1.223" /config/*.yaml /config/packages
(no output)
$ cat /config/.storage/http
  "use_x_forwarded_for": true,
  "trusted_proxies": ["192.168.1.223/32", "192.168.20.33/32"],
  "yaml_migration_done": true
```

Home Assistant 2026.9.4 holds its HTTP settings in `.storage/http`, migrated from YAML
earlier. Adding a new `http:` block to `configuration.yaml` would put a second source next to
the migrated one, and which of them wins on this version is not established; editing
`.storage/http` instead is a different change from the one approved (it needs Core stopped,
not only restarted, because Core rewrites `.storage` from memory). So I stopped and asked.
The lead's decision: Igor's approval covers the change (add 192.168.20.4/32 and
192.168.20.3/32, remove 192.168.1.223/32); the method is the lead's to choose, and the
lead chose editing `.storage/http` with Core stopped. The lead confirmed nothing else
service-affecting was running.

### Before

`/config/.storage/http`, root 0600, 624 bytes, 2026-08-27 20:47. Checked for secrets before
recording (the only match for password/token/secret/key is `"key": "http"`); valid JSON
(`python3 -m json.tool` on the laptop). Relevant part:

```
"server_port": 8123,
"use_x_forwarded_for": true,
"trusted_proxies": ["192.168.1.223/32", "192.168.20.33/32"],
"ip_ban_enabled": true,
```

`https://home.ryzhkov.dev/` through public-api (`--resolve home.ryzhkov.dev:443:192.168.20.33`): 200.

### Calls (on `home-assistant`, which has `jq`)

```
ha core stop                                       # issued 20:30:30, returned 20:30:48
cp -p /config/.storage/http /config/.storage/http.bak-2026-10-02
jq '.data.stable.trusted_proxies = ["192.168.20.33/32","192.168.20.4/32","192.168.20.3/32"]' \
   /config/.storage/http.bak-2026-10-02 > /config/.storage/http.tmp
jq -e .data.stable.trusted_proxies /config/.storage/http.tmp && cat /config/.storage/http.tmp > /config/.storage/http
rm /config/.storage/http.tmp
ha core start                                      # issued 20:30:48, returned 20:31:03
```

The same edit made on a copy on the laptop validated with `python3 -m json.tool`, and its
diff against the original touched only the `trusted_proxies` lines. Writing with `cat >`
kept the file's owner and mode (root, 0600).

### After

- `/config/.storage/http` after start: 651 bytes, still
  `["192.168.20.33/32","192.168.20.4/32","192.168.20.3/32"]`; Core did not rewrite it.
- `https://home.ryzhkov.dev/` through public-api: 200 at 20:31:07; `/manifest.json` 200.
- `ha core logs`: no line from `homeassistant.components.http` and none mentioning
  `trusted_prox` or `X-Forwarded` (count 0). The only warnings after start are the existing
  `dreame_vacuum` invalid entity ID notices.

Downtime: Home Assistant was unavailable from 20:30:30 (stop issued) to 20:31:07 (first 200
through public-api), about 37 seconds.

Recorded answer: Home Assistant now trusts both edge VMs and the VIP; 192.168.1.223 is no
longer trusted.

### Rollback

```
ha core stop
cat /config/.storage/http.bak-2026-10-02 > /config/.storage/http
ha core start
```

## 3. gaming-pc ufw rule for 18800

### Before

`sudo ufw status numbered`: 48 rules, the relevant one
`[43] 18800/tcp ALLOW IN 192.168.20.33 # bellerophon-cartest via edge traefik`, followed by
the IPv6 rules `[44] 53317/udp (v6)` to `[48] 4242/udp (v6)`. The full listing is in
`proposals/unifi-edge.md`, section 4, and was unchanged since.

### Call

```
sudo ufw allow proto tcp from 192.168.20.4 to any port 18800 comment "bellerophon-cartest via edge traefik (public-api-b)"
-> Rule added
```

### After

`sudo ufw status numbered`: 49 rules; `diff` against the before listing shows only the new
rule inserted, with the IPv6 rules renumbered from 44-48 to 45-49:

```
[43] 18800/tcp   ALLOW IN   192.168.20.33   # bellerophon-cartest via edge traefik
[44] 18800/tcp   ALLOW IN   192.168.20.4    # bellerophon-cartest via edge traefik (public-api-b)
```

From public-api-b, `curl http://192.168.90.212:18800/` returns 303 (the cartest app's
redirect), so both the UniFi policy and the host rule admit .4.

### Rollback

```
sudo ufw delete allow proto tcp from 192.168.20.4 to any port 18800
```
