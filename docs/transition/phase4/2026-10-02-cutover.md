## Outages

None observed. The watch loop made 638 requests between 20:56:06.9 and 20:59:27.1, across the
shutdown, the start and the hand-back, and all 638 answered 200. A second loop (0.5 s interval)
across the section 3 hand-over and hand-back (20:54:50 to 20:55:50) recorded 119 requests,
all 200. public-api's Traefik was stopped for about 20 s (20:55:04 to about 20:55:23) while
public-api-b held the VIP, so no client noticed it.

Failover time: from `qm shutdown` to public-api-b's MASTER state, 1.34 s. From public-api's
last advertisement (priority 0 at keepalived's stop) the takeover is immediate. No request
failed. The hand-back with `nopreempt` took 0.55 s (restart issued 20:59:14.99, MASTER on
public-api 20:59:15.54).

Not a failover outage, recorded so it is not mistaken for one: `auth`, `rss` and `ai` were
failing before the cutover (backends on homelab) and still are.

## Deny VRRP from the AdGuard CTs

The Proxmox CT firewall was not used. Reasons, checked on both nodes:

- The CTs' NICs carry no `firewall=1` (`pct config 100`, `107`, `201`), so enabling it means a
  `pct set ... net0` on each running DNS CT, which re-plugs its veth through a firewall
  bridge; with `ip=dhcp` inside, each CT loses its link for a moment and might not renew.
- The datacenter firewall is off (`pve-firewall status`: `disabled/running`,
  `/etc/pve/firewall/` empty). Turning it on is cluster-wide: it brings in host rules on both
  nodes unless each gets a `host.fw` with `enable: 0` first, and it starts filtering VMs 101,
  102 and 106, whose NICs already carry `firewall=1`. proxmox-firewall (nftables) 1.2.3 is
  installed and enabled beside pve-firewall 6.0.5, so which backend renders the rules also
  needs settling first.
- Even with it, a rule dropping protocol 112 does not stop a compromised CT from claiming
  192.168.20.3 with gratuitous ARP, which needs no VRRP at all; that takes `ipfilter` and MAC
  filtering on DHCP-addressed CTs.

Used instead: `check_unicast_src` in every edge's `vrrp_instance`
(`roles/keepalived/templates/keepalived.conf.j2`). keepalived ignores an advertisement whose
source is not in `unicast_peer`, so the CTs, or anything else on VLAN 20, cannot take part in
the election. This is a change on the edge VMs, not on the hypervisors; no hypervisor
configuration changed. Remaining risk, recorded: a host on VLAN 20 that forges the peer's
source address, or answers ARP for the VIP, can still divert edge traffic. Closing that needs
the CT firewall with `ipfilter` and `macfilter`, as a planned change with a window for the
three DNS CTs and the cluster firewall decided first.
